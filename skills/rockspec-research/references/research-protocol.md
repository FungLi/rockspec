# 业务研究协议

## 状态

- `READY_FOR_REQUIREMENTS`：问题空间和证据足以开始需求澄清。
- `MORE_RESEARCH_NEEDED`：已形成部分结论，但指定未知仍可能改变决策。
- `NO_ACTION_RECOMMENDED`：证据表明当前不值得进入研发，或问题应由非产品方式解决。
- `BLOCKED`：关键证据需要用户授权、领域专家、数据访问或外部状态变化。

## 1. 决策导向

将宽泛主题改写为可以停止的研究问题：

```text
我们需要了解 <问题>，以便决定 <决策>，适用于 <人群/范围>，基于 <时间窗口>。
```

明确不研究什么、谁会使用结论，以及什么证据足以改变或支持决策。若一个问题包含多个相互独立的决策，拆成多个研究问题并排序。

## 2. 证据层级

按主张类型选择拥有该事实的来源：

1. 内部事实：产品遥测、业务数据库、支持工单、销售记录、合同、当前产品行为和已批准文档。
2. 用户与领域知识：原始访谈、问卷回答、会议记录和领域专家陈述。
3. 外部规则：法律法规、标准组织、监管机构和官方政策。
4. 外部产品事实：厂商官方文档、定价、Release Note、公开接口和第一方公告。
5. 技术事实：源代码、正式 Spec、官方 API 文档和可重复实验。

二手文章、聚合报告和搜索摘要只能作为线索或明确标记的二手证据。竞争对手的一方描述只能证明其公开声称了什么，不能证明实际采用率、效果或用户满意度。

每个来源记录：标题或标识、所有者、路径/URL、发布日期或数据时间窗口、访问日期、适用范围、限制和新鲜度。

## 3. 结论类型

- `FACT`：来源直接支持、适用范围明确的事实。
- `USER_REPORT`：某位用户或某组样本的原始陈述。
- `INFERENCE`：由多个事实推导出的解释，必须列出推导依据。
- `HYPOTHESIS`：尚待验证、但值得检验的可能解释或机会。
- `UNKNOWN`：当前证据无法回答的事项。

置信度使用 `HIGH/MEDIUM/LOW`，表示当前证据对该范围内主张的支持程度，不表示主张重要性。不得用高置信度掩盖过小样本或过期数据。

## 4. 业务探索维度

根据研究问题选择相关维度，不要求机械填满：

- 角色、目标和 Jobs-to-be-Done。
- 当前端到端工作流、触发点和交接。
- 业务对象、术语、所有权和生命周期。
- 显式规则、例外、失败与边界场景。
- 痛点的频率、严重度、持续时间和受影响范围。
- 当前替代方案、手工补偿和不行动成本。
- 商业、运营、合规、渠道和技术约束。
- 能证明改善的领先与滞后信号。

对含糊术语提出一个准确替代，并使用具体场景验证。例如，不接受未定义的“客户”“订单有效”“完成”等词。发现代码、文档、指标和访谈互相冲突时，记录各自来源、影响和需要谁裁决。

## 5. 提问纪律

事实能从环境、仓库或来源查到时自行查证。只有方向、价值权衡、范围选择或来源访问需要用户决定时才提问。每次只问会显著改变研究路径的一个问题；次要细节采用明确假设并标记为 `HYPOTHESIS`。

## 6. 停止条件

以下条件全部满足时停止：

- 研究问题得到与决策相关的回答，或明确证明当前无法回答。
- 所有重要主张都有逐项来源或明确的非事实标签。
- 术语冲突、来源矛盾和样本限制已显式说明。
- 剩余 `UNKNOWN` 有负责人、获取方式或不再阻塞的理由。
- 新增一份同类证据不太可能改变当前建议。

研究不是为了消灭所有未知。达到停止条件后不得继续扩张到相邻市场、功能或技术方案。

## 7. 交接

报告只提出“是否值得进入 Requirements”和需要保留的证据边界，不编写 Requirement、技术方案或 Task。用户选择继续时，`rockspec-requirements` 从磁盘读取研究报告，将 `FACT/USER_REPORT/INFERENCE/HYPOTHESIS/UNKNOWN` 的区别保留到假设和开放问题中。
