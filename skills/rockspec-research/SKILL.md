# RockSpec 业务研究

只产出一个结果：足以支持下一项业务决策、且每个重要结论都可追溯的研究基线。

## 边界

- 这是探索与研究，不是 Requirements、Design 或实施。可以读取仓库、文档、数据和外部来源，但不得修改产品代码或自动创建 Change。
- 首版保持 Inline，不创建后台 Research Subagent。事实由 Agent 查找，业务决策由用户作出；不得把可自行查证的问题转交给用户。
- 研究产物是有时间边界的输入，不是永久事实。来源过期、业务变化或样本不足时必须重新验证。

## 执行

1. 先明确研究要支持的决策、目标受众、范围、时间边界和停止条件。问题过宽时帮助拆分；需要用户决定研究方向时，每次只问当前最重要的一个问题。
2. 从磁盘重新读取已有 PRD、Spec、研究、领域词汇、产品行为、指标定义、支持或销售材料；检查同一概念在文档、代码和用户表达中的冲突。
3. 建立证据计划：优先使用内部一手数据和记录、用户或领域专家原始陈述、官方文档、法规/标准、源代码和第一方产品资料。二手资料可以帮助发现线索，但重要主张应回到拥有该事实的来源。
4. 围绕角色、目标、当前工作流、触发条件、业务规则、痛点频率与严重度、现有替代方案、边界场景、约束和成功信号收集证据。不要因模板完整而虚构信息。
5. 使用 `FACT`、`USER_REPORT`、`INFERENCE`、`HYPOTHESIS`、`UNKNOWN` 标记每项重要结论，并记录来源、时间、适用范围和置信度。用户陈述可以是一手定性证据，但不能自动推广为所有用户事实。
6. 主动澄清含糊或重载术语，用具体场景检验角色、规则和边界；将来源矛盾并列展示，不通过平均或措辞掩盖冲突。
7. 当研究问题已有可行动答案、重要主张有证据、矛盾已显式化、剩余未知有负责人或验证方式，且继续收集不再可能改变当前决策时停止。无法满足时输出 `MORE_RESEARCH_NEEDED` 或 `BLOCKED`，不得无限扩张。
8. 从 [research-report.md](assets/research-report.md) 写入 `.rockspec/workbench/research/<slug>/research.md`，并生成带来源时间和可选 Change 关联的 `receipt.yaml`。执行前读取 [research-protocol.md](references/research-protocol.md)。

报告研究状态、问题与决策、证据覆盖、业务现状、术语与规则、洞察、矛盾、未知和建议下一步。只有用户决定进入研发时，才将报告交给 `$rockspec-requirements`；研究结论不能替代 Spec Approval。
