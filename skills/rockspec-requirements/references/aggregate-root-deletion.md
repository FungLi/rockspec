# 聚合根删除模式

当用户要求永久删除一个业务对象及其关联数据时，用本模式把业务意图与数据库机制分开。不要把一次具体故障中的表名或锁策略推广为所有项目的固定实现。

## 行为契约

先从领域关系和现有产品规则确定：

- **聚合根**：用户实际选择删除的业务对象。
- **Owned dependents**：只归属于该聚合、没有独立生命周期的数据；聚合删除成功后必须一起消失。
- **Retained references**：平台资源、模板、用户、审计、知识或其他具有独立生命周期的数据；不得因聚合删除而消失。
- **Shared or contradictory relations**：无法证明唯一归属的关系；采用既有领域政策，缺少政策且会造成不同数据损失结果时才形成用户决策。
- **Eligibility and authority**：谁能删除、哪些状态允许删除，以及是否不可逆。

Spec 描述可观察后置条件：成功后聚合根和全部 owned dependents 不存在，retained references 不变；失败时不产生部分删除。用户只需决定会改变数据归属、保留集合、不可逆性或外部结果的事项。

## 工程责任

FK cascade、显式依赖顺序、行锁、advisory lock、隔离级别、重试、Repository 拆分和测试屏障属于 Design。只要它们实现同一业务后置条件，就由技术设计者选择、独立 Reviewer 验证，不向产品用户逐项确认。

“一起删除”“不要把流程做复杂”等表达通常表示不增加用户可见的逐条处理、冻结或拒绝流程；它不等于禁止内部使用必要的锁、约束或重试。只有内部机制会改变外部结果、兼容性、重大运行成本或需要接受剩余风险时，才重新形成产品决策。

## Reviewer 检查

- Spec 不应出现类、文件、SQL 顺序、锁层级或数据库算法禁令。
- Design 必须证明所有 owned dependents 都受同一原子边界保护，并覆盖并发和失败测试。
- 技术证明缺失但业务后置条件不变时，Finding 路由到 `design.technical`，分类为 `derived_gap + authority_impact: unchanged`；不得重开 Requirements 让用户选择技术机制。
