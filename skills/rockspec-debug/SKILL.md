# RockSpec 调试

只产出一个结果：有可重复证据支持的根因诊断，以及明确且可验证的下一步。

## 边界

- **Diagnose（诊断）**：用户只要求分析原因时，完成诊断报告后停止。
- **Diagnose and Fix（诊断并修复）**：用户同时要求修复时，仍必须先确认根因，再把报告交给现有 Change、Task 或 `$rockspec-triage`；诊断阶段不得直接修改业务行为。
- 迭代诊断保持 Inline：反馈环、假设验证和探针的中间态必须留在主循环，逐轮决定下一步；不得拆给 Subagent，否则会丢失中间状态并反复交接。临时探针可以写入受控范围，但必须带唯一标记并在结束前清理。
- 一次性只读事实核对可外包：需要通读多个模块、调用链、配置或相邻实现才能确定的**只读、单次、无需用户 Authority** 的事实核对，派只读 Subagent 完成，主上下文只保留结论和证据锚点（`file:line`），不保留通读过程。判据是「只读 + 单次 + 不改变诊断迭代的中间态」；凡涉及迭代推进、探针决策或需要用户拍板的判断，一律保持 Inline。

## 执行

1. 固定用户报告的实际症状、影响、环境、时间范围和已尝试操作。展示日志、命令或抓包前先删除 Secret、Token、Cookie、认证头和个人数据。
2. 建立一个能命中准确症状的反馈环，优先使用失败测试、CLI/HTTP 脚本、浏览器脚本、Trace Replay、最小 Harness、差分或 Bisection。必须实际运行并证明它能够变红；无法建立时记录尝试并请求缺失的环境或脱敏证据，不得猜测。
3. 重复运行并最小化复现。一次只移除一个输入、调用方、配置或步骤，直到剩余元素都与失败有关。
4. 阅读完整错误和调用链，检查最近变更、环境差异、依赖与工作示例；跨组件系统在边界采集输入、输出、配置和状态，沿坏数据或错误状态逆向追到来源。
5. 证据已经指向一个原因时写出单一可证伪假设；原因仍有竞争解释时列出 3 至 5 个排序假设。每个假设声明预测，一次只用一个最小探针验证，不叠加猜测性修复。
6. 只有反馈环、因果链和假设预测共同成立时才确认根因。任何修复失败都使诊断失效并返回调查；三次修复尝试仍失败时停止并提出架构讨论，不继续试错。
7. 从 [debug-report.md](assets/debug-report.md) 写入 `.rockspec/workbench/debug/<slug>/report.md`，证据放入同目录 `evidence/`，并生成引用活动 Change/Task 或外部来源的 `receipt.yaml`。完整过程读取 [debug-protocol.md](references/debug-protocol.md)。
8. Diagnose and Fix 模式下，活动 Task 的实施缺陷路由到 `$rockspec-implement`；需求或设计缺陷路由到对应能力；没有受治理 Change 时将报告交给 `$rockspec-triage`。修复必须先加入正确接缝上的失败回归测试，再通过原始反馈环验证。

报告诊断状态、反馈环命令、最小复现、证据、已验证根因、被否证假设、临时探针清理状态和下一负责 Skill。没有确认根因时不得使用 `DIAGNOSED` 或提出确定性修复。
