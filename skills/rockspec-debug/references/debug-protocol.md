# 调试协议

## 状态

- `INVESTIGATING`：正在建立反馈环或收集证据。
- `BLOCKED`：缺少能够复现或区分假设的环境、权限或脱敏证据。
- `NOT_REPRODUCED`：已完成约定范围的调查，但反馈环未命中用户症状。
- `DIAGNOSED`：根因已由反馈环、因果链和可证伪预测共同确认。
- `FIX_VERIFIED`：下游修复已通过回归测试和原始反馈环；诊断本身不能提前声明此状态。

## 1. 固定症状

记录预期行为、实际行为、影响用户或系统、首次出现时间、频率、环境、版本和准确错误。区分观察事实与用户推测。不得把“附近的另一个失败”当成目标故障。

所有证据先脱敏。命令优先读取环境变量，不把凭据写入参数、脚本、报告或聊天。只引用携带诊断信号的最少日志行。

## 2. 建立反馈环

按以下顺序寻找最窄且真实的接缝：

1. 现有或新增失败测试。
2. CLI、HTTP 或固定 Fixture 脚本。
3. 浏览器自动化，断言 DOM、Console 或 Network 的准确症状。
4. 真实请求、事件或 Trace 的脱敏 Replay。
5. 最小服务或函数 Harness。
6. Property/Fuzz、Bisection 或新旧版本差分。
7. 有明确步骤和证据回传的人机循环。

反馈环完成条件：有一条已执行命令，能命中准确症状，重复运行结果稳定，速度足以支持多轮验证，并可由 Agent 无人值守执行。偶发故障以固定种子、压力或循环提高复现率，不要求伪造 100% 确定性。

## 3. 最小化与定位

一次只删减一个变量并重新运行。检查完整错误、Stack、最近 Commit/Diff、配置、依赖版本和环境差异。寻找同仓库中可工作的相似路径并逐项比较。

多组件路径在每个边界记录：

- 输入与输出。
- 配置和环境是否正确传播。
- 状态、时序和标识是否保持一致。
- 第一个从正确变为错误的位置。

错误发生在深层时沿调用者和数据来源逆向追踪，直到找到最初引入错误值、状态或时序的地方。表现点不是自动等于根因点。

## 4. 假设实验

每个假设使用以下形式：

```text
如果 <原因> 成立，那么 <最小操作> 将导致 <可观察预测>。
```

直接证据已收敛时测试一个假设；证据仍分叉时列出 3 至 5 个假设并按解释力、证据和验证成本排序。每次只改变一个变量。失败实验必须更新证据和排序，不能在原修复上继续叠加修改。

性能问题先建立基线、Profiler 或 Query Plan，再执行 Bisection；不要用大量日志代替测量。临时日志统一使用唯一前缀 `[ROCKSPEC-DEBUG-<id>]`。

## 5. 根因门禁

只有同时满足以下条件才能标记 `DIAGNOSED`：

- 原始反馈环稳定命中用户症状。
- 报告给出从触发条件到症状的完整因果链。
- 已确认假设的预测被实验观察到。
- 主要替代假设有被否证或降级的证据。
- 建议的修复点位于根因所有者，而不是仅压制表现。

外部、环境或时序原因也必须记录调查边界、证据和可操作处理，例如监控、超时、重试或错误信息；不得把“没有找到”改写成“外部原因”。

## 6. 修复交接与清理

诊断阶段只允许不会改变产品行为的探针。交接前删除所有 `[ROCKSPEC-DEBUG-<id>]` 日志、临时 Harness、抓包和未脱敏文件；有长期价值的最小复现应在下游实施中转成正式回归测试。

路由规则：

- 当前 Task 的实现错误：`rockspec-implement`。
- Requirement 错误或遗漏：`rockspec-requirements`。
- 架构、接口或 Design 错误：`rockspec-design`。
- Task 边界或依赖错误：`rockspec-plan`。
- 无活动 Change：`rockspec-triage`，由 Triage 决定 Lite/Standard/Strict。

修复后重新运行最小回归测试和未经最小化的原始反馈环。任一仍失败都回到 `INVESTIGATING`。
